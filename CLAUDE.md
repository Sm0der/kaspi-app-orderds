# ARTROOM/OPS — заказы Kaspi, склад и производство

Сервис для мебельного производства: забирает заказы из Kaspi, помогает их собрать и
отгрузить, ведёт склад, цеха, себестоимость и аналитику владельца. Владелец — Sm0der,
два магазина на Kaspi: **КухниKZ** (merchant 30322035) и **ART ROOM HOME** (30178171).

Весь код и комментарии — на русском. Пиши так же.

---

## Правила владельца — нарушать нельзя

1. **Ничего не переименовывать.** Названия изделий склада, товаров каталога и изделий
   технолога владелец меняет сам. Названия на Kaspi — его маркетинговый инструмент, а не
   описание товара: один шкаф намеренно продаётся под разными именами и ценами. Даже
   явная опечатка или «Комод  МФ» с двумя пробелами — не трогать, можно только сказать.
2. **Изделия склада не объединять.** Объединение удаляет изделие-источник, его имя
   перестаёт существовать — а имя печатается на коробке. Если нужна общая себестоимость,
   вешай **один код технолога на несколько изделий**, это поддерживается.
3. **На этикетке не должно быть артикула Kaspi.** Только название изделия и наш код
   технолога (SH-4001). Один шкаф продаётся под разными карточками и ценами, и артикул на
   коробке выдаёт это покупателю.
4. **Статус ARRIVED в Kaspi** («товар поступил») отправляется только при явном
   подтверждении человека, что товар физически есть. Никогда автоматически.
5. **Секреты не печатать.** Пароль базы, JWT-секрет и токены Kaspi не выводить в
   сообщения, не коммитить, не подставлять в файлы. Значения лежат только в `.env`.
6. Деструктивные операции на боевой базе (удаление, массовое обновление) — только с
   подтверждения владельца. База одна и она боевая, тестовой нет.

## Из чего состоит

Три деплоя на Vercel, **одна** база Supabase (проект `aiatnvqgghdkzrbuqcmw`).

| Часть | Где | Что это |
|---|---|---|
| Дашборд заказов | `frontend/` | Next.js, интерфейс: отгрузка, CRM, архив, себестоимость, аналитика, админ-панель |
| API заказов | `server/` | Express: синхронизация с Kaspi, накладные, CRM, аналитика, себестоимость |
| Склад и производство | `production/warehouse-production-app/` | Next.js 16 + Prisma: этикетки, приёмка, отгрузка по сканеру, цеха, админ-разделы |

**Один домен.** Склад собран с `basePath: '/sklad'`, дашборд проксирует туда `/sklad/:path*`
через `rewrites()` в `frontend/next.config.js` (адрес в `WAREHOUSE_URL`).

**Один вход.** Токен выдаёт склад (`/api/auth/login`, JWT HS256), дашборд и Express
проверяют его тем же `JWT_SECRET` — он обязан совпадать в трёх местах и в обоих проектах
Vercel. Один origin — один `localStorage`, ключи `token` и `user` общие.
Единственная таблица людей — `production_users`, Supabase Auth не используется.
Роли (7 штук) и права на разделы — в одном справочнике `src/lib/roles.ts` склада.

**Грабля basePath:** он не действует на `fetch`. Со страниц склада все запросы идут через
`apiUrl()` из `src/lib/session.ts`, иначе `/api/...` уедет в дашборд.

## Данные

**Кто чем владеет.** `stores`, `orders`, `order_items`, `products` пишет только
синхронизация с Kaspi в `server/` — склад из них читает, писать нельзя, следующий синк
перезапишет. Своё у склада: `warehouse_items`, `warehouse_item_skus`, `barcodes`,
`workshops`, `production_*`, `order_picking*`, `label_batches`.

**Три кода одного изделия:**
- **артикул Kaspi** — `products.sku`, свой в каждом магазине;
- **изделие склада** — `warehouse_items` + `warehouse_item_skus` (у изделия много
  артикулов, у артикула одно изделие: `UNIQUE(store_id, sku)`);
- **код технолога** — `cost_products.code` (`SH-4001` = категория, двери, ящики, номер;
  пятая цифра — цветовое исполнение).

Код технолога висит на **изделии склада** (`warehouse_items.cost_product_id`) — это якорь.
Оттуда он автоматически раскладывается по артикулам изделия (`products.cost_product_id`)
через `src/lib/costLink.ts`, потому что **маржа в аналитике считается по строке заказа, а
строка знает только артикул**. Правишь связь — вызывай `syncProductCostLinks`.

**Штрихкод = одна ШТУКА, а не коробка.** Если изделие едет в трёх местах, один код
печатается на всех трёх этикетках с «1 из 3». Ищется по точному `barcode_value`, формат не
разбирается — поэтому старые напечатанные этикетки продолжают работать.

## Как запускать локально

Три процесса, порты важны (`frontend/.env.local` ждёт именно их):

```bash
npm --prefix server run dev                                  # API, порт 3001
npm --prefix production/warehouse-production-app run dev -- -p 3210
npm --prefix frontend run dev                                # дашборд, порт 3000
```

Нужны три файла с секретами, **их нет в git** — переносить руками:
`server/.env`, `frontend/.env.local`, `production/warehouse-production-app/.env.local`.
Ключи: `DATABASE_URL`, `JWT_SECRET` (одинаковый везде), `KASPI_API_TOKEN_*`,
`NEXT_PUBLIC_API_URL`, `WAREHOUSE_URL`.

`server/.env` по умолчанию смотрит в локальный Postgres (`localhost:5433`), которого
обычно нет. У склада `.env.local` смотрит на **боевой Supabase** — оттуда и берут
`DATABASE_URL`, когда нужно что-то проверить на реальных данных:

```bash
DATABASE_URL="$(grep '^DATABASE_URL' production/warehouse-production-app/.env.local | cut -d= -f2- | tr -d '"')" node …
```

Проверка интерфейса склада без пароля: подписать себе JWT тем же `JWT_SECRET`
(`{userId, email, role: 'ADMIN'}`, jose, HS256) и положить в `localStorage` как `token`.

## Скрипты и разовые операции

| Что | Как |
|---|---|
| Импорт таблицы технолога | кнопка «Импорт» в «Себестоимости» или `runImport()` из `server/services/costingImport.js` |
| Цены с Kaspi | `node server/scripts/fetch-product-prices.js [--apply]` |
| Фото товаров | `node server/scripts/fetch-product-images.js [--apply]` |

**Оба скрипта про Kaspi запускать только с обычного IP, не с сервера:** публичный каталог
Kaspi блокирует дата-центры (Vercel получает 429 с HTML-страницей защиты). Официальный API
заказов при этом работает — это разные системы защиты.

## Грабли, которые уже стоили времени

**Kaspi API**
- **Во всех запросах шлём заголовок `X-Merchant-Uid`** с номером магазина
  (`stores.kaspi_merchant_uid`) — так ответила поддержка Kaspi 23.09.2026: по нему они
  определяют, от имени какого магазина обрабатывать запрос. Одного `X-Auth-Token` им
  недостаточно. Заголовки собирает `KaspiService` (клиент и `authHeaders()` для запросов
  мимо него — накладные качаются напрямую, это PDF). Руками заголовки не собирать.
- Фильтр по дате создания заказа — максимум **14 дней**, это ограничение их API.
- `POST /orders {status: ARRIVED}` по существующему заказу иногда отвечает
  `404 Order not found` — предсказать по полям заказа нельзя, в кабинете те же заказы
  формируются нормально. Логика: пробуем, на 404 отправляем человека в кабинет. Владелец
  написал в поддержку 18.09.2026, и ответом как раз стал `X-Merchant-Uid` — если отказы
  прекратятся, причина была в нём.
- **Накладная появляется не сразу: до 3 минут.** Замерено по 316 заказам (момент нажатия
  «сформировать» против `/CreationDate` внутри самого PDF): у 69% накладная готова за
  15 секунд, но у каждого двадцатого - через 1-3 минуты, 90-й процентиль ровно 179 секунд.
  Отсюда два следствия. Первое: `confirmAssembledInKaspi` ждёт 5 секунд и такие заказы не
  ловит - они уходят в «не прошёл», хотя накладная выйдет. Второе, важнее: **повторный
  ASSEMBLE выпускает ВТОРУЮ накладную с новым номером**, поэтому на ошибку формирования
  нельзя отвечать повторной отправкой - сперва подождать 3 минуты и перечитать заказ.
- **Накладную Kaspi отдаёт только пока заказ на складе.** После передачи курьеру (у нас
  стадия `shipping`) тот же адрес отвечает `404 Some error occurred`, и так навсегда -
  проверено 06.10.2026 на 40 живых заказах: скачался ровно один, единственный в стадии
  `packed`. Отсюда два следствия. Время формирования (`/CreationDate`) надо успеть
  прочитать до отгрузки - поэтому `syncAll` дочитывает штампы сам, а не ждёт кнопки
  «Прочитать» в «Вывозах». И неудачу надо запоминать (`orders.waybill_stamp_failed_at`):
  без этого кнопка каждый раз перебирала одни и те же безнадёжные заказы, счётчик не
  двигался, и она выглядела сломанной.
- Kaspi переписывает `courierTransmissionPlanningDate` под факт, поэтому просрочку по их
  данным посчитать нельзя — завели свою `orders.ship_date_first`, заполняется один раз.
- **Номер карточки ≠ артикул продавца**, хотя выглядят одинаково (карточка 166513982, наш
  артикул на ней 335962720). Номер карточки лежит в заказе:
  `order_items.raw_data.relationships.product.data.id`, base64. По нему берутся и цена, и
  фото — точно, без поиска по названию. Поиск по названию однажды поставил толстовку на
  комод: у модели пять цветов, «похожая» картинка хуже, чем никакой.
- Своё предложение на карточке ищем по `merchantId` + `merchantSku`; предложения отдаются
  страницами по 20 и сортируются по цене. Позиции переезжают между двумя нашими
  магазинами, поэтому ищем любое наше предложение на карточке.

**Время**
- База хранит время в **UTC**, Алматы = **+5**. Показываешь владельцу — прибавляй 5 часов.
- День заказа считать из epoch `creationDate`, а не из `order_date` (там у старых заказов
  UTC, у новых алматинская полночь), и обязательно `::text` в SQL — иначе node-pg сдвинет
  дату на сутки.
- Колонки с моментом времени — только `timestamptz`.

**Prisma**
- **Никогда не запускать `prisma db push`** в приложении склада: его схема описывает чужие
  таблицы (products, stores) лишь частично, и push предложит снести `cost_products`,
  `app_users` и половину колонок. Менять структуру — сырым SQL (`$executeRawUnsafe`), потом
  вручную привести `schema.prisma` в соответствие и сделать `prisma generate`.
- Таблиц `products` / `cost_products` в схеме склада нет — к ним только сырые запросы.

**Объём и скорость**
- В `orders` лежит **история за 2025-2026** — 39 тысяч заказов, залитых разово
  (`server/scripts/import-kaspi-history.js`, журнал партий в `history_import`,
  откат одной командой `--rollback <batch>`). Фильтр Kaspi смотрит назад только на 14 дней,
  но само окно можно двигать в прошлое — так история и была собрана.
- **Рабочие экраны не должны касаться архива.** «Недавние» заказы определяем по
  `order_date`, а не по `updated_at`: заливка проставила архивным строкам сегодняшний
  `updated_at`, и сводка главного экрана начала тянуть всю таблицу — 31 секунда вместо двух.
- По той же причине не пишем `stage NOT IN (...)`: список стадий закрыт, перечисление
  рабочих (`IN ('new','accepted','packed','shipping')`) даёт тот же набор, но по индексу.
- Страницу списка отбираем ДО присоединения `order_items`. Джойн ко всей таблице с
  `GROUP BY` и `LIMIT` в конце на 39 тысячах строк стоил 8 секунд.
- «Аналитика» фильтрует период по дню, вычисленному из `raw_data`. Для таких выражений
  заведены индексы (`idx_orders_created_day`, `idx_orders_handed_day`); без них каждый
  запрос перебирал таблицу целиком, распаковывая jsonb построчно.
- **Функции должны жить рядом с базой.** Supabase в Токио, поэтому у `server/` и у склада
  в `vercel.json` стоит `hnd1`. Когда API стоял во Франкфурте, каждый поход в Postgres
  шёл через полмира, а их на один эндпоинт несколько: перенос ускорил всё примерно вдвое.
- Аналитика за период в два года считается ~11 секунд (`maxDuration` стоит 60) — там
  восемь независимых проходов по 39 тысячам строк. За 30 дней — около секунды.

**Прочее**
- В кодах технолога у владельца встречается кириллица, неотличимая на вид (`КМ-0411`,
  `ТВ-0208`) — при сохранении приводим к латинице (`normalizeCode`).
- Код технолога без спецификации даёт «себестоимость» из одних тарифов (~3000 ₸) —
  в аналитике такой считаем неизвестным, иначе прибыль выходит почти равной выручке.
- Токены магазинов наружу отдаются только последними 4 символами.
